# Кастомные (premium) эмодзи с автоматическим fallback — дизайн

Дата: 2026-09-19. Статус: согласован с автором шаблона (вариант «прозрачный middleware»).

## Проблема

Боты на шаблоне используют обычные юникод-эмодзи в кнопках и текстах и выглядят как все.
Хочется единый минималистичный набор иконок (пак custom emoji `tgiosicons`,
https://t.me/addemoji/tgiosicons), причём так, чтобы:

1. ИИ-агент **всегда** использовал этот набор, не зная ID и не изучая новый API;
2. при окончании Telegram Premium у владельца бот **сам** переходил на обычные эмодзи,
   а при возобновлении — сам возвращался к иконкам.

## Что даёт Telegram (проверено по Bot API)

- **Тексты:** HTML-тег `<tg-emoji emoji-id="ID">📊</tg-emoji>` (Bot API 6.2). Обычный эмодзи внутри
  тега обязателен и является штатным fallback: если бот не имеет права на custom emoji, сервер
  молча убирает entity, клиент показывает обычный эмодзи. Ошибки нет.
- **Кнопки:** поле `icon_custom_emoji_id` у `InlineKeyboardButton` / `KeyboardButton`
  (Bot API 9.4, aiogram ≥ 3.30). Отдельное от `text`, fallback-механизма нет. Поведение сервера для
  бота без права — не документировано: либо иконка молча отбрасывается, либо приходит ошибка.
  Дизайн обязан выдерживать оба варианта.
- **Право на custom emoji:** владелец бота с активным Premium (или username с Fragment); только в
  сообщениях, которые бот шлёт напрямую в личку/группу/супергруппу. Через `getMe` право не узнать.

## Цели

1. В коде хендлеров и клавиатур — **только обычные юникод-эмодзи**, как сейчас. Никаких ID, тегов
   `<tg-emoji>` и `icon_custom_emoji_id` руками. Правило для агента одно: «эмодзи — из списка
   `app/ui/icons.py`».
2. Конвертация в custom emoji происходит на выходе, в session-middleware, для текстов, подписей и
   inline-кнопок.
3. Право на custom emoji определяется автоматически по живому трафику и обновляется без рестарта:
   потеря Premium → обычные эмодзи, продление → иконки.
4. Владелец видит текущий режим в `/admin` и получает одно уведомление при переключении в fallback.
5. Каталог иконок воспроизводим: `just emoji-dump [pack]` печатает `эмодзи → ID` для любого пака.

## Не цели

- Reply-клавиатуры (`KeyboardButton`) не конвертируются: их `text` — это payload, который вернётся
  боту как сообщение, и хендлеры матчат его строго (`F.text == CANCEL_PICK_TEXT`). Обычный эмодзи
  в них остаётся. Расширение — отдельная задача.
- Инлайн-режим (`answer_inline_query`), инвойсы, `answer_callback_query`, описания команд —
  entities там не поддерживаются, не трогаем.
- Эмодзи в логах (`logger.info("🚀 …")`) — не UI, не трогаем.

## Каталог `app/ui/icons.py`

- Источник ID — пак `tgiosicons`, выгрузка `just emoji-dump tgiosicons`.
- Все эмодзи, которые сейчас встречаются в UI шаблона (кнопки, тексты хендлеров, отчёты сервисов),
  попадают в `EMOJI_TO_ICON`. Для эмодзи без аналога в паке берётся ближайший по смыслу
  (например 🩺 → иконка «пульс/статистика», 👑 → «звезда», 👻 → «блок/запрет», 🚀 → «молния»);
  выбор фиксируется комментарием в `Icons`.
- Правило для регекса: длинные варианты (с VS16) матчатся раньше коротких.
- `emojify` идемпотентна и **не трогает** содержимое уже существующих `<tg-emoji>`, а также
  `<code>` / `<pre>` (custom emoji внутри моноширинных блоков не нужен и может конфликтовать
  с entities).

## Middleware: поток одного запроса

```
исходящий метод
  │
  ├─ не Send*/Edit* с text/caption/reply_markup, или parse_mode не HTML,
  │  или переданы явные entities → пропустить как есть
  │
  ├─ status.enabled?  ── нет → пропустить как есть (обычные эмодзи; раз в RETRY_AFTER — попробовать)
  │
  ├─ text/caption → emojify(); reply_markup (inline) → iconify_markup()
  │      (эмодзи в начале текста кнопки вырезается, ставится icon_custom_emoji_id)
  │
  ├─ make_request(изменённый метод)
  │      ├─ TelegramBadRequest, текст ошибки про icon/emoji → status.disable(reason),
  │      │    повторить make_request(исходный метод) один раз
  │      └─ успех: если мы вставили ≥1 <tg-emoji>, а в Message.entities /
  │           caption_entities нет ни одного type == "custom_emoji" → status.disable(reason)
  │
  └─ вернуть ответ
```

Детали:

- **Состояние** `CustomEmojiStatus` (в процессе, singleton в модуле middleware — как `liveness`):
  `enabled: bool = True`, `disabled_at: datetime | None`, `reason: str | None`,
  `RETRY_AFTER = 24 ч`. `enabled` считается `True`, если `disabled_at is None` или прошло больше
  `RETRY_AFTER` — так продление Premium подхватывается без рестарта. При рестарте — снова `True`.
- **Детекция по entities** — основной механизм, работает для обоих вариантов поведения сервера с
  кнопками: первое же текстовое сообщение с иконкой выявляет отсутствие права. Цена потери
  Premium — максимум один экран с кнопками без эмодзи (если сервер молча отбрасывает иконки) или
  один повторный запрос (если сервер отвечает ошибкой).
- **Уведомление админам** при `disable`: один раз за период отключения, всем админам
  (`settings.admin_user_ids` + `db.get_admins()`), фоновой задачей через `asyncio.create_task`
  (сообщение проходит через тот же middleware, но флаг уже выключен — рекурсии нет). Текст:
  «Иконки переключены на обычные эмодзи: Telegram не принял custom emoji. Обычно это значит, что
  у владельца бота закончился Premium. Проверим снова через 24 ч». Лог — `warning`.
- **Повторная попытка при ошибке** — только один раз и только для методов, которые мы изменили;
  ошибки без слов `icon`/`emoji`/`entit` пробрасываются как есть.
- **Ответ `True`** (редактирование inline-сообщения) — детекции нет, ничего не делаем.
- `CUSTOM_EMOJI=off` — middleware не регистрируется вообще; бот работает как сейчас.

## Правило для агента (в AGENTS.md / CLAUDE.md)

- В кнопках и текстах используй обычные эмодзи из списка `SUPPORTED_EMOJI` в `app/ui/icons.py`.
  В кастомные иконки они превратятся сами. Эмодзи в inline-кнопке — первым символом текста.
- Нужен эмодзи, которого нет в списке: сначала найди ближайший в списке. Если не подходит —
  `just emoji-dump tgiosicons`, добавь ID в `Icons` и пару в `EMOJI_TO_ICON`, тест каталога
  подтвердит согласованность. Эмодзи вне списка уйдёт обычным — это допустимо, но не по умолчанию.
- Не пиши `<tg-emoji>` и `icon_custom_emoji_id` руками.
- Reply-клавиатуры и `answer_callback_query` — обычные эмодзи, конвертации нет.

## Тестирование

Юнит-тесты `tests/test_icons.py` (чистые функции):

- `emojify`: замена известного эмодзи, вариант с/без VS16, идемпотентность, неизвестный эмодзи
  не трогается, содержимое `<tg-emoji>`, `<code>`, `<pre>` не трогается.
- `iconify_markup`: эмодзи в начале текста → `icon_custom_emoji_id` + текст без эмодзи; эмодзи не
  в начале или неизвестный — кнопка без изменений; `ReplyKeyboardMarkup` возвращается как есть;
  счётчик изменённых кнопок.
- Согласованность каталога: каждый ключ `EMOJI_TO_ICON` ссылается на существующий атрибут `Icons`,
  ID — строка из цифр, `SUPPORTED_EMOJI` совпадает с ключами.
- Инвентарь: все эмодзи, встречающиеся в `app/keyboards/**` и `app/handlers/**` в строковых
  литералах UI, есть в `EMOJI_TO_ICON` (список исключений — явный, в тесте).

Тесты middleware через харнес `tests/test_custom_emoji.py`:

- `premium=True`: `/admin` → кнопка уходит с `icon_custom_emoji_id` и текстом без эмодзи,
  текст — с `<tg-emoji>`; `status.enabled` остаётся `True`.
- `premium=False`: после первого сообщения `status.enabled == False`, следующие клавиатуры уходят
  с обычным эмодзи, `<tg-emoji>` в тексте нет; уведомление админу отправлено ровно один раз.
- Сервер отвечает `TelegramBadRequest("... custom emoji ...")` на метод с иконками → повтор без
  иконок, `status.enabled == False`.
- Прошло больше `RETRY_AFTER` → `enabled` снова `True`, конвертация возобновляется.
- `parse_mode="Markdown"` / явные `entities` → метод не изменён.
- Существующие тесты, проверяющие текст кнопок (`"📊 Рассылка" in buttons_of(...)`), переводятся на
  режим харнеса `premium=False` по умолчанию, чтобы оставаться независимыми от каталога; тесты
  иконок включают `premium=True` явно.

`just check` зелёный после каждого шага.

## Риски и допущения

- Поведение `icon_custom_emoji_id` для бота без права известно только эмпирически после
  первого запуска; дизайн покрывает оба варианта. После реализации проверить на боте, владелец
  которого без Premium, и зафиксировать наблюдение комментарием в middleware.
- Апгрейд aiogram 3.20 → 3.31: прогнать полный `just check`; изменения между версиями в
  используемых API (Router, FSM, RedisStorage, session middleware) — совместимые в рамках 3.x,
  но проверить `CHANGELOG` на breaking changes.
- ID custom emoji стабильны, но пак сторонний: если автор пака удалит стикер, клиент покажет
  fallback-эмодзи из тега; для кнопок — иконка пропадёт. Каталог обновляется `just emoji-dump`.
